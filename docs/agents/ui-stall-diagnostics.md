# UI stall diagnostics

Item `ui-freezes-intermittently-for-several-seconds-at`; spec `ui-stall-tooling-spec` rev 1.8 (user 2026-11-04 19:00:43Z "we need to build tooling into the frontend to determine the cause"). Code: `apps/desktop/renderer/src/stallwatch.ts` (+ `stallhook.ts`, `streamerstats.ts`, `stallfixture.ts`), `apps/desktop/main/stall-log.ts`, `stall-probe.ts`, `stall-worker-source.ts`, `packages/contracts/stall.ts`. Tests: `renderer/tests/stallwatch.test.tsx`, `tests/stall-log.test.mjs`, `tests/stall-probe.test.mjs`, `tests/stall-fixture.test.mjs`.

**Add `data-stall-id` to every new text input** (value from a fixed set: `desk-composer`, `quickchat`, `mail-reply`, `mail-compose`, `docket-field`, `hubchat-composer`, `search`, `settings-field`, `ask-answer`). A stall record names the typing target by it, never by text or name.

## What is written

`<data root>/diagnostics/ui-stalls.jsonl`, written ONLY by main (`stall-log.ts`), one JSON object per line, `v:1`. Rotates past 2 MB to `.1` then `.2` (three files, at most 6 MB). A line is at most 16 KB (stacks are cut first: 40 frames of 200 characters, then scripts, then whole arrays; `truncated:true`). At most 30 lines a minute per process; the overflow is counted in the next line's `dropped`. Best effort: a write error is swallowed. Nothing is written while nothing stalls. `ORGTREE_STALLWATCH=0` switches the whole tooling off (no observers, interval, worker, ping, header or command-line switch; the preload gets `--orgtree-stallwatch=0`).

Common fields: `at` (ISO UTC of the stall start), `src`, `ms`, `window` (the window-events id: the app's own UUID, kept as is; anything else is dropped), `org_window`, `app` (version and short commit), `dropped`, `truncated`.

| `src` | Found by | Body |
| --- | --- | --- |
| `renderer-loaf` | a `long-animation-frame` entry of 500 ms or more (shorter ones only bump `loaf_50_500`) | `loaf{blocking,render_start,style_layout_start,render_at,style_layout_at,scripts_ms,scripts_n,scripts[]}` (top 10 scripts: invoker, fn, app-relative url, position, ms, forced style/layout ms, `at` = start offset in the frame; `render_at`/`style_layout_at` are offsets from the frame start, null without a rendering update; `scripts_ms`/`scripts_n` total EVERY listed script, not only the top 10; Chromium lists only scripts of 5 ms or more), `gpu{cpu_pct,window_ms,restarted,ws_mb}` (main's sample of the GPU process, below), `input[]` (Event Timing entries overlapping the stall: type, input_delay, processing, presentation, `target`), `keys_2s`, `field_len` (focused field, rounded down to 100), `fetch[]` (unsettled engine calls, route and age), `ws{frames,bytes}`, `react{commits_in,commits_2s}`, `ctx{screen,panel,popout}`, `selectionchange{in,before_2s}`, `counts{agents,projects,watchdogs,open_panels,dom_nodes,text_nodes,max_depth,dom_partial,heap_mb,highlight_ranges,draft_saves_10s}`, `streamer{...scans and masks overlapping the stall...}`, `loaf_50_500`, `capture_ms` |
| `renderer-ping` | main pings each visible org window every 500 ms over a MessagePort answered from the preload (on the renderer's main thread); no pong 400 ms after a ping is a stall | `blocked_ms`, `stacks[]` (the renderer's JS stack at 400 ms and again at 2000 ms, at most twice; `unavailable:<reason>` if the API fails), `ipc[]` |
| `renderer-unresponsive` | Chromium's own `unresponsive` event | as `renderer-ping`, one stack |
| `main-lag` | a 100 ms main interval whose tick is 500 ms or more late | `lag_ms`, `ipc[]` (handlers pending or running in the window), `main_stack` (a worker thread pauses main through an inspector session; the worker is LAZY - about 8 MB resident, so it never starts in the first 60 s after launch (startup sync IPC and engine attach look like stalls; a `main-lag` record in that window carries `unavailable:startup-grace`), then starts on the first stall signal and stops after 10 quiet minutes; the stall that starts it has `unavailable:none-captured`; at most once a minute, never leaves the debugger enabled; `unavailable:<reason>` on any failure) |
| `sync-ipc` | a `sendSync` handler that took 100 ms or more | `channel` |
| `process-gone` | Electron's `child-process-gone` (GPU, utility, ...) or a window's `render-process-gone`, except `clean-exit` | `kind` (`renderer`, `GPU`, `Utility`, ...; else `other`), `reason` (Electron's enum; else `other`), `exit_code` |
| `stall-trace` | main finished a stall trace (below) | `file` (bare name in `diagnostics/stall-traces/`), `events`, `bytes`, `caught` (the stall it waited for happened inside it), `canvas_bg`; a lost capture writes `failed: true` and `stage` (`stop` or `process`) instead, and leaves no file (the next prune also clears an empty file or `.raw-*` left by a run cut off mid-capture) |

`gpu` (recorder v2, on `renderer-loaf`, `renderer-ping`, `renderer-unresponsive` and `main-lag`): main reads the GPU process's cumulative CPU with `app.getAppMetrics()` every 5 s (`GpuSampler`, main/stall-probe.ts, a ring of 13); a record gets `cpu_pct` (percent of one core) over `window_ms`, from the last sample at or before the stall start to when the record reached main, `restarted` (the GPU pid changed: no CPU compared) and `ws_mb` (working set). Numbers only; nulls when there is no GPU process.

**The attract trace is NOT in this file.** `src:'attract'` records (attract mode's own steps, kinds and timings only) go to `diagnostics/ui-attract.jsonl` with their own rate bucket (30/min) and rotation (1 MB x 2): attract lines can never use the freeze budget or rotate freeze evidence out.

## Stall traces (4.6.1)

Item `hang-every-time-a-new-desk-loads-especially-whil`. Code: `apps/desktop/main/stall-trace.ts`, wired in `main/index.ts`; tests `tests/stall-trace.test.mjs` (TR1-TR7) and `renderer/tests/stallcanvasbg.test.tsx`.

- **Armed by a frame that waited:** a `renderer-loaf` of 500 ms or more with `loaf.blocking` under 50 and `scripts_ms` under 20 % of `ms`. That stall has already ended, so it starts an Electron `contentTracing` capture; the next waiting frame lands inside it. The capture stops 3 s after that frame, or at 20 s.
- **Bounded:** one capture per 10 minutes, three per run; categories `gpu`, `cc`, `viz`, `benchmark`, `toplevel`, `disabled-by-default-gpu.service`, `disabled-by-default-viz.gpu_composite_time`; a 32 MB trace buffer (record-until-full); the newest three files kept. `ORGTREE_STALLTRACE=0` turns only this off (`ORGTREE_STALLWATCH=0` turns everything off).
- **Private:** the raw recording is streamed line by line through `filterTraceLine` (allowlisted categories, numeric args from a fixed key list, identifier-shaped names, process/thread names; no URLs, free text or Chromium metadata) into `diagnostics/stall-traces/<UTC start>.json.gz` and then deleted. The file is `{"meta":{...},"traceEvents":[...]}`: `meta` holds the arming and caught frames' numbers, the app version and `canvas_bg`.
- **`canvas_bg`** (also on every `renderer-loaf`): `{theme, webgl}`, the background actually MOUNTED (`[data-canvas-bg]`, or `.canvas-bg` without it = `dots`; `none` when no canvas is on screen) and whether the ascii layer's WebGL canvas exists.
- **Reading:** open the `.json.gz` (gunzip it first) in Perfetto or `about://tracing`; look at the GPU process's and the compositor's slices across the caught frame's wall time.
- **Measured cost** (Session 0, software GL, 60 fps synthetic page, 2026-11-15): frame mean 16.67 ms with and without tracing (p95 16.7 to 16.8 ms); CPU of all app processes 3.8 % to 4.0 %; a 10 s capture was 55 MB raw and 2.7 MB gzipped, filtered in 5.4 s with no main-thread lag; start 29 ms, stop 1.9 s.

## GPU shader cache (4.6.1)

- **Electron 44.11.3 keeps Skia's compiled shaders between launches** in `<userData>/GrShaderCache` (Electron 44.4.4, electron/electron#54161; 44.2.0 named no such folder). The 4.6.1-alpha.1 trace `2026-11-16T09-38-30Z` had desk and window loads waiting 0.3 to 1.4 s in `RasterDecoderImpl::DoEndRasterCHROMIUM::Flush` while ANGLE compiled 23 new programs. Measured 2026-11-16 on a private desktop, NVIDIA GPU, scratch userData, a 36-tile page of desk effects: 44.11.3 run 2 stored 3 of 51 programs (longest flush 21 ms, run 1 269 ms); 44.2.0 stored 51 both runs (258 ms). A trace with `GrShaderCache::store` inside each long flush on every start means the cache is not being kept. Tile raster stays on the GPU (USER 2026-11-16 09:43:35Z: no CPU raster).

- **The shader warm-up (4.6.1, `main/shader-warmup.ts`).** The cache is cold after an install, an Electron update or a GPU driver update, and on 4.6.1-alpha.2's first launch each of the 16 stalls of 500 ms or more lined up with a newly saved GrShaderCache entry. So once per app version + Chromium + GPU driver, 15 s after launch and once the user has been idle for 5 s, main draws `renderer/shader-warmup.html` (the real canvas, nodes and desks over a synthetic org; no preload, no engine, no network) in an offscreen-rendered window that is never shown. Each desk of the scene waits until frames are quick again (6 in a row under 50 ms), so on a GPU where a compile takes 200-850 ms the scene waits for them instead of being cut off. The window is destroyed when the scene sets its done title, or after 45 s (8 s until 4.6.2: 4.6.1-alpha.3 was cut off on the user's machine). `<userData>/shader-warmup.json` records the key it ran for and the creation time of the GrShaderCache folder it warmed; a folder recreated since (on 4.6.1-alpha.2 it was, at 2026-11-16 21:03Z, cause not reproduced) runs the warm-up again; `ORGTREE_SHADER_WARMUP=0` turns it off; each run writes one `shader-warmup` line (outcome, `ms`, `window_ms`, and `cache_birth`/`cache_bytes`: the GrShaderCache folder's creation time and size, so a changed creation time between two launches is a wiped cache) to ui-stalls.jsonl. Two measured traps: `app.getGPUFeatureStatus()` reads all-software until the GPU process is up, so it is read after `getGPUInfo`; and shaders compiled for an in-memory (off-the-record) session are never written to GrShaderCache, so the window uses its own `persist:` partition and clears its storage after each run.

## How to read a stall

**Waiting vs working (v2).** `loaf.blocking` 0 means no task, rendering included, reached 50 ms: the renderer's main thread was free. If `scripts_ms` is also small next to `ms`, the frame waited on frame delivery (GPU process, compositor, OS), which no renderer entry sees; then read `gpu.cpu_pct` and look for a `process-gone` line. `render_at` near `ms` with a small `ms - render_at` puts the time before rendering; script `at` offsets show whether the scripts were spread out or bunched (alpha.5 10:22Z: 613 ms, blocking 0, 80 ms of scripts, v1 could not say more).

Join lines by `window` and overlapping time: a `renderer-loaf` says WHICH script and which input; a `renderer-ping` from the same window says what the renderer was running while it was blocked; `main-lag` and `sync-ipc` say whether main (or a synchronous IPC) held the window. `input[].input_delay` large with `processing` small means the thread was already busy when the key arrived. `streamer.scans_in` and `max_scan_ms_in` show whether the streamer scan was running during the stall; `counts` show what had grown.

**Function names are minified or empty** (production builds minify; most listeners are anonymous). The attribution path is the `app:/` `line:col` of a ping stack frame, plus the LoAF `sourceCharPosition`, mapped through the sourcemap of the SAME build (UI stall spec rev 1.5). To map: load that build's renderer `.map` (for example with the `source-map` package: `new SourceMapConsumer(map).originalPositionFor({ line, column: col - 1 })`; stack-frame lines and columns are 1-based and the library's `column` is 0-based, hence `col - 1`; a `sourceCharPosition` is a character offset into the bundle, so convert it to line/column first) and read the original file and function. A log without its build's sourcemap names only minified functions.

## Redaction (an allowlist, applied in main before writing)

Only schema fields are written; unknown keys are dropped; an enum value outside its enum becomes `other`. Script paths: the app origin or install folder becomes `app:/`, no query or fragment, any other absolute path is redacted. Fetch routes: `/api/orgs/<org>`, and every segment after `agents|projects|mail|work|watchdogs|files|apps` is `<id>`. Every other free string (function names, frames, channels, reasons) goes through `packages/contracts/streamer.ts` with all types on, whatever the user's switches say, each match becoming `<redacted:kind>`. Never recorded: message, mail, transcript or docket bodies, request or response bodies, WebSocket data, key values, field contents, clipboard, titles, agent or org names (counts only).

## Test-only fixture

`ORGTREE_STALL_FIXTURE=busy` at build time defines `__ORGTREE_STALL_FIXTURE__` and compiles in `stallfixture.ts`: a keydown in the desk composer spins 1500 ms in `stallFixtureBusy`, for rig proof RP1. A normal build defines `''` and the bundler drops it (`tests/stall-fixture.test.mjs`).
