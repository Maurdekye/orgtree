# Desktop and Python engine contract

The Python process retains the real orgtree.api domain and serves the copied existing UI. Relative HTTP, WebSocket, download, image and HTML URLs remain browser transport. IPC is only for native lifecycle/settings/setup operations.

## Managed startup

- Launch engine/launch.py with an absolute, real Python interpreter (packaged engine/runtime/python.exe). The engine package contains its own backend/orgtree source; v1 repository is never a runtime dependency.
- Main validates an explicit v2 data root, including existing symlink resolution, before spawning. It rejects the v1 root and ancestor/descendant overlap. Fresh startup uses a separate application data directory; import is a later Settings action owned by the engine.
- Env: ORGTREE_DATA is the resolved v2 root, ORGTREE_V2_UI_DIR the built renderer directory, ORGTREE_V2_TOKEN a fresh main-only credential. Engine must validate root BEFORE importing legacy storage and REMOVE the token from os.environ before importing modules that spawn children.
- Engine binds 127.0.0.1 on a first port PREFERRED from 20000-49151 (below the Windows dynamic range, whose Hyper-V/WinNAT reservations shift on every boot) — 64 candidates are probed there and an OS-assigned port is taken if none is free, so the range is a preference, not a guarantee. It persists the port in engine-port.json under the explicit v2 root and reuses it on later fresh launches. A live listener on the stored port refuses startup instead of changing the browser storage origin or attaching to another process. This preserves the existing localStorage namespace for drafts and layout; two-launch application verification remains required. A stored port refused with access-denied (WSAEACCES inside a reserved range) cannot serve the UI on this boot and no amount of waiting changes that, so the engine chooses and persists a fresh port; any other bind failure refuses startup, because moving the origin makes whatever the browser stored under the old one unreachable — storage is per origin, so it is stranded rather than deleted. The move is noted on stderr, which the main process currently discards. Ready line: {"type":"ready","protocol":1,"port":12345,"pid":123,"dataRootId":"resolved absolute data root"}. Main checks PID, root, port and protocol. Other stdout lines are ignored with a bounded line buffer; logs must never carry credentials.
- Electron main remains alive in tray after normal close. The single-instance lock routes another launch to the existing window; there is no unauthenticated .port discovery or orphan-engine attachment.

## Boot host and authenticated attachment

- engine/service_host.py is a headless launcher for the boot-time Scheduled Task "Orgtree Background Engine" (S4U as the user's own account, no stored password anywhere). The ALL-USERS installer owns the task lifecycle (build/installer.nsh): registration on install, stop-before-copy and re-register + restart on update (including fresh-install start, paired with the desktop root-owned refusal and bounded re-attach path), stop + delete on real uninstall — all guarded to the all-users install mode and running under the installer's existing elevation. tools/register/unregister-boot-engine.ps1 are the equivalent manual operator scripts and tools/boot-task-probe.ps1 is the bounded pre-registration S4U viability probe with rollback. The running APPLICATION never registers, elevates or stops the task itself.
- The host owns exactly what desktop main owns today: a fresh per-boot credential and the readiness handshake. launch.py keeps the guardian, root lock, port persistence and every route. The host pins ITSELF as the guardian-watched parent, so a killed host means a terminated engine tree, never an orphan. Requested shutdown exits 0 so restart-on-failure settings do not resurrect a deliberately stopped engine; engine failure exits nonzero.
- After — and only after — the ready line, the host writes engine-attach.json under the data root: {type:"attach",protocol:1,port,enginePid,hostPid,dataRootId,token,startedAt}. engine-port.json is NEVER authoritative for attachment (a persisted port may have moved during this very startup). The descriptor carries the token in a unique temporary created with a protected operator/SYSTEM/Administrators DACL, the operator stamped as its explicit OWNER, and no sharing. The owner is set at creation because the boot task's S4U logon of an administrator account can default new files to BUILTIN\Administrators even at LeastPrivilege, which the desktop's authentication check refuses; read-back verifies owner and DACL before publication retains both.
- Desktop attachment trust is TWO DISTINCT CHECKS, named for what they actually prove. AUTHENTICATION is the descriptor file's NTFS owner: the owner SID must equal the current user's before the token is sent anywhere — everything inside the descriptor and the identity response is authored by whoever wrote the file, so trust reduces to write access, and the owner check is what turns "a file existed" into "the operator's host wrote it". The subsequent GET /api/desktop/identity round-trip (token-gated; must echo protocol 1, the descriptor's enginePid and the canonical root) is a STALENESS check — it catches a recycled port and a previous boot's file, and authenticates nothing. Cross-account attack is reasoned from NTFS ownership, not measured (single-account machine). HARD DEPLOYMENT REQUIREMENT: the data root (default %APPDATA%; ORGTREE_V2_DATA can move it) must not be writable by other accounts, and the boot host must run AS the operator, unelevated — an Administrators-owned descriptor is refused. Any doubt — bad owner, missing listener, 401, protocol/process/root mismatch — declines with a recorded diagnostic and falls back to a fresh managed spawn; the engine-side root lock arbitrates races, and a structured stdout refusal from the losing spawn triggers a bounded re-attach (budget exceeds the host's readiness timeout) instead of a fatal dialog.
- Write access to the descriptor also buys DENIAL of boot startup, not only desktop hijack: the host's stale-descriptor check stands down (exit 1) for a live verified answer on the descriptor's port, so an attacker who can write the file can stop the boot engine from ever starting — the same write boundary F1's trust check protects, and one more reason an unsafe root is refused rather than tolerated.
- An attached engine is not stopped by window close, quit or exit-on-close. Its liveness is watched: failed stats trigger an identity probe, and a lost engine starts autonomous recovery — re-attach (the port persists, so usually the same origin with a NEW token; session signing reads live engine values), else a managed spawn, else a bounded wait on a host mid-restart; the app reloads on the same origin and relaunches on a changed one. Updates while attached stop the engine through its authenticated shutdown route and VERIFY it stopped before quitAndInstall — an unverifiable stop refuses the update (maintenance requests land in their designed failure report; the idle auto-path retries later) — and the elevated installer stops the task before file replacement (with a bounded wait for actual engine-tree process termination), re-registers it from a task XML (S4U principal captured pre-elevation, ExecutionTimeLimit PT0S, restart-on-failure, IgnoreNew) and starts it after successful registration, including a fresh installation.
- S4U consequences stay explicit: the host fills missing profile variables (APPDATA/LOCALAPPDATA/HOME from USERPROFILE) for its children; no DPAPI/Credential Manager/EFS, no Windows-integrated network auth (an NTLM-authenticating proxy is a documented breaking condition). Provider HTTPS uses application bearer tokens and is expected to work; the probe, not this sentence, is the evidence.
- LAYERED STOP PROTECTION — an architectural dependency both halves rely on (opus R2): the desktop's pre-update stop proof (connection-level endpoint death + descriptor removal + guardian root-lock release, the lock being decisive) is the FIRST gate, whose job is to avoid handing a live engine to the installer at all. For ALL-USERS installations and updates, the AUTHORITATIVE gate before file replacement is the elevated installer's own preflight (task disable, real process-tree wait under $INSTDIR, hard fail on timeout) — including manual all-users runs the desktop never sees. This preflight is gated to all-users mode and does not protect per-user updates: the desktop stop proof must independently fail closed on missing or unknown guardian-lock evidence. The REVERSE dependency also holds and is equally binding: the installer may start the boot task unconditionally on a fresh install ONLY because the desktop's refused-spawn → bounded re-attach path (the root-owned refusal code) resolves the resulting root-lock race; narrowing or removing that retry breaks fresh-install autostart.
- SETUP/RUNTIME PRIVILEGE BOUNDARY (user requirement 2026-09-09): elevation happens exactly once, at all-users install/update/uninstall time, inside the installer's own UAC flow — task registration, stop-before-copy and removal live there. EVERYTHING at runtime is unprompted and non-interactive: the boot task starts the engine with a Limited-run-level S4U logon of the selected user (no password, no logon session, no UAC), the desktop attaches with an ordinary user-mode owner query plus token header (no elevation), stop/restart of the engine goes through the authenticated shutdown route or the host's own lifecycle (never runas), and recovery/spawn fallback runs as the user. A normal Windows boot or unattended restart must produce a serving engine with ZERO prompts and no interactive login; packaged acceptance includes that no-interactive-prompt boot check. Anything discovered to require interactive action at runtime (e.g. a provider re-authentication) is reported as a concrete deviation, never papered over as autonomous.

## Browser and native boundaries

- Main registers the owning app window and blank portal children. Its session hook authenticates exact loopback HTTP/WS only for the owning top frame, initial app navigation, and portal stylesheet/font/image requests; embedded frames are never signed. Headers are stripped before every other destination. Actual Electron probes cover trusted HTTP/CSS/WS plus foreign-frame and srcdoc negative controls.
- Every engine browser route validates credentials, including files and WS. Missing Origin is NOT proof of authorization. MCP requires existing or newly scoped per-agent credentials bound to org/node/generation. Desktop operator credential never enters provider/MCP child environment.
- Preload exposes window.orgtreeDesktop only on the top-level engine UI. Native handlers also verify sender webContents, top frame and UI route. Blank portal children and embedded HTML have no bridge; preload compares the full expected origin including port. HTML presentation windows use separate sessions with one initial exact-wrapper-URL GET capability. All child engine requests are blocked; internet resources are permitted without desktop credentials. Captured actual _mockup_wrapper output is exercised, but real production API wrapper execution remains an integration check.
- Native blank child windows preserve the existing owner-mounted DOM portal. No new React App or engine session is mounted in the child. Actual Electron primitive test preserves the same input node and draft; full renderer integration remains separate evidence.

## Lifecycle and packaging

- Preferences: Start at login ON, Exit on close OFF. Dev builds never register electron.exe at login. Main close preserves all popouts. Exit-on-close applies only when the last visible view closes. Explicit quit first dispatches orgtree:before-exit for synchronous layout saving, then requests authenticated POST /api/desktop/shutdown. Before domain imports the launcher calls engine.process_lifetime.arm_process_lifetime(root, parent_pid). A separate guardian holds the exclusive .desktop-engine.lock and a Windows kill-on-close Job containing engine and future descendants; it observes pinned engine/desktop process handles and terminates the tree before unlocking. Four real Windows process tests include children/grandchildren, duplicate-root refusal and reuse, normal exit, engine crash, desktop death and guardian crash; removal of kill-on-close is caught by mutation. Launcher wiring is present; real-provider lifecycle remains an integration check. Non-Windows startup explicitly refuses process ownership until a native adapter exists; no unsafe PID-based fallback is used. Guardian preparation is acknowledged before assignment. A timeout after acknowledgment never kills the guardian to report failure; startup exits nonzero while ownership remains intact. Delayed Windows termination writes .desktop-engine-status.json after ten seconds and retains the root lock until termination is confirmed.
- GET /api/desktop/status returns {activeAgents,totalAgents,idle}. Unknown/stale/unavailable state is never interpreted as idle. Idle update application also requires 60 seconds of OS user inactivity, then graceful engine stop. Packaged GitHub prerelease updater is enabled; actual signed update execution is not claimed by fixture tests.
- Installer defaults current user, permits all-users choice; unsigned prototype accepted. Runtime must preserve a real interpreter directory so sys.executable -m orgtree.mcptool works.
- Harness setup detects presence only and links official Claude Code, Codex and Antigravity setup. No CLI installation, login, provider calls or multi-account registry.

## Source replies

ReplyContext identifies source by org/agent/generation/eventId and bounded quote. Engine resolves authoritative source/role and validates identity; quote is never authorization. Renderer owns context menu/removable preview/source jump. Preserve replyTo in drafts, reload/popout transfer, outgoing mail and durable receipt.

## Scope and deadline

Deadline is 2026-09-08 01:00 UTC (04:00 Israel), not restarted by approval or seed. Preserve/improve existing UI, SQLite data contracts, integrated Docker-free hub, multi-provider support, history until removed, full copy import including active-work resumption. Deferred/removed: all account management/fallback, mobile, Git management, public/kiosk exposure and all agent-execution sandbox/isolation. Electron renderer isolation remains an OS-bridge boundary, not agent execution isolation.

Native notifications default to questions, urgent mail and ticket attention. Routine mail/completion is configurable (routineNotifications=false). No system sleep blocker is installed. Uninstall keeps user data. Login startup is quiet tray. The official Python3.13.15 embedded archive is checksum-pinned by tools/provision-runtime.py; its app-local dependency manifest records versions and hashes. Python-served UI is packaged as resources/ui, outside app.asar.

Quiet login exposes getWindowState() with restoreWindows=false until manual show. Main emits main-window-shown when the user opens it; renderer owns restoring saved external views. Explicit Quit/update ignores renderer beforeunload vetoes after saving layout, so a stopped engine cannot leave an unclosable window. Independent actual-App active-org/settings-popout/draft checks established clean exit before this native window-state addition.

Native maintenance requests are authorized/durable in the engine. Status may carry maintenance {id,action:restart|update,target:org|mailhub|both,reason}; Exact-id desktop POST /api/desktop/maintenance/ack sends {id,outcome:execute|up-to-date} and must return accepted:true before action. Execute acknowledgment atomically rechecks idle and holds admission; up-to-date completes only an update request without an admission hold because no restart follows. Electron acts only with engine idle and OS idle60s. Update checks cannot reuse their pre-check idle observation; application waits for a fresh sample. Native Electron owns relaunch/updater helpers outside the Python Job; copied V1 Git/update scripts are never the V2 maintenance route.

Trusted about:blank portals share same-origin opener and adopted DOM authority. They have no direct preload bridge, but are NOT an isolation boundary: real Chromium attributes a child executeJavaScript fetch and cloned stylesheet to the owning App frame, and those requests are signed. Untrusted HTML always uses the separate artifact session/sandbox, never an adopted portal.

If an acknowledged native restart/update throws, or its acknowledgment response is lost, Electron reports the exact request ID to operator-only POST /api/desktop/maintenance/failure. A released:true response completes reporting; the engine records terminal failure and releases only that request's admission hold. Electron saves unreported IDs in userData/maintenance-failures.json and retries only reporting after the engine returns, even when no request is pending or agents are busy. It never repeats uncertain native execution. Automatic update application remains paused across launches until a new explicit update request; failure is shown in the native app. The receipt is necessary when the updater throws after engine shutdown. Focused controller tests cover both throwing operations, lost acknowledgment, unavailable failure endpoint and recovery across controller recreation; actual cross-process wiring remains acceptance-owned.
